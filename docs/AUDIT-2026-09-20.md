# RAAKA review — 2026-09-20

Reviewed baseline: **0.1.0**, commit **c28af38**. This review covers every
tracked application, geometry, configuration and documentation file, the
existing tests, the running interface and published CI results. It records
findings and proposals; application fixes are not part of this documentation
change. The implementation order is in [Roadmap](ROADMAP.md).

## Assessment

The separation between the pure generator, semantic pieces and Three.js is a
good foundation. The reference-inspired support vocabulary is recognisable,
and the restrained interface already provides a useful place to study form.
Keep those decisions. The product is currently a single-recipe interactive
study, with no saved projects, drawing export or manufacturing export.

Make measurements reliable and studies recoverable next, followed by one
complete geometry-to-output workflow. Silos should be the next new recipe
after Piloti. Bring the first SVG output forward instead of making it wait
for all six recipe families.

## Verified baseline and limits

- `pnpm verify` passed: ESLint, both application and tooling TypeScript
  checks, six Vitest tests in two files, `tsc -b` and the production build.
- The installed compiler is TypeScript 6.0.3. Strict checks are enabled by
  the TypeScript 6 default, despite no explicit `strict` property in either
  configuration. Explicit `--strict` checks passed for both projects, and the
  compiler API reported `strictNullChecks` and `noImplicitAny` as true.
  The initial suspicion that strict checking was disabled was rejected.
  See the [TypeScript 6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html).
- `pnpm audit --prod --json` reported zero known advisories across four
  production dependencies. This is a dated registry result, not a guarantee
  about future advisories or a review of every development dependency.
- A diagnostic sweep called the real generator for 27,000 combinations:
  seeds 0–499, support counts 1–6, asymmetry 0/0.12/0.5 and neck ratios
  0.18/0.34/0.7, with other parameters at their defaults.
- For the first five seeds of that sweep, 270 studies were additionally
  checked against the actual frustum mesh builder. All 1,890 frustums had
  outward-facing triangles and two oppositely directed uses of every mesh
  edge. Mesh-integrated piece volumes matched reported totals to a maximum
  relative difference of approximately `1.25e-8`. This validates individual
  pieces, not a boolean-unioned manufacturing solid.
- Browser checks confirmed default readings, seed changes, object selection,
  lost state after reload and stale selection after changing support count.
  A 390-pixel viewport confirmed hidden navigation without page overflow;
  the temporary viewport override was reset. No warnings or errors were
  reported by the inspected browser log.
- The initial main-branch Verify run passed. Dependency pull-request runs
  have a separate confirmed secret-scanning configuration failure (A03).

The diagnostic sweep is review evidence, not a committed regression suite or
an exhaustive geometry proof. It holds overall proportions and height fixed.
Future fix tests must cover those limits too. No physical casting, load test,
plotter run, Kerros transfer or Muusia transfer was performed. The owner's
visual feedback remains to be incorporated.

## Confirmed findings

P1 means an incorrect result or a blocked core workflow. P2 means a usability,
robustness or implementation gap to address during the next feature work.

### A01 — P1: Envelope does not measure the complete sculpture

`src/core/generator.ts` returns the upper box width as `widthMm`, while
`src/App.tsx` presents it as the overall envelope. Shifted shoulders can extend
outside that box. The sweep found 12,489 width mismatches; this is a count in
the chosen diagnostic grid, not an estimate of real-world frequency.

Reproduce from a fresh page: choose one support, neck width 0.18, asymmetry
0.50, leave height at 1,500 mm and click Next seed once (319). The display
reports **1,080 mm**, but all generated corners span **1,434.231 mm** in X.
The largest mismatch in the sweep was seed 220 with the same settings:
**1,080 mm reported versus 1,607.998 mm actual**.

Proposed fix: derive min/max bounds from all semantic geometry, including
offsets. Keep upper-mass dimensions as separate recipe parameters. Use actual
bounds for displayed dimensions, framing and exports. Add this fixture and
range tests to the permanent test suite.

### A02 — P2: The shadow camera excludes the entire default model

`src/components/Viewport.tsx` configures the directional light's horizontal
shadow bounds but leaves its depth range at the installed Three.js defaults:
near 0.5, far 500. Default-model corners are approximately 2,547–4,282 units
away along the light camera's viewing direction. They cannot enter its shadow
map. Enabling `castShadow` and `receiveShadow` does not fix that range.

Proposed fix: fit shadow bounds and depth to the sculpture and relevant ground
receiver, update the projection and verify contact shadows at both 1 m and
2 m heights. Review the hemisphere light's Y-up default against the Z-up scene
at the same time. Light orientation is a visual tuning question; the shadow
depth exclusion is measured.

### A03 — P1: Pull-request secret scanning fails before scanning

The `secrets` job in `.github/workflows/verify.yml` does not pass the action its
automatic GitHub token. A dependency PR's log explicitly reports that
`GITHUB_TOKEN` is required to scan pull requests. Its corresponding push run
passes; a green push does not establish that PR verification works.

Evidence: [failed PR run 35479325505](https://github.com/Bambi8000/raaka/actions/runs/35479325505).
Six Dependabot PRs were open at review time. None were merged during this review.

Proposed fix: follow the action's token contract and provide only the required
read permissions; confirm success on both push and pull-request events,
including a Dependabot PR. Keep scanning enabled. Review the queued action
updates separately; do not combine unrelated major upgrades with this fix.

### A04 — P1 product gap: A study cannot be recovered or revisited

`src/App.tsx` stores only live React state. Reloading a study at seed 319
returned it to default seed 318. There is no save, open, undo, autosave,
editable seed or previous-variant control. The seed alone is insufficient to
reproduce a study if its parameters are not also recorded.

Proposed milestone: a versioned project file with recipe ID, recipe version,
seed, parameters and later semantic operations. Add local recovery, explicit
save/open, editable seed, reset and undo/redo. Treat a slider drag as one undo
step. Validate files before replacing the current study and preserve the
current state when a load fails. Add round-trip tests.

### A05 — P2: Selection, editing scope and camera movement are coupled

- `Viewport` selects on `pointerdown`, including the beginning of an orbit
  gesture. A drag over a piece can change the selection unintentionally.
- Select Support 3, reduce Supports to 1, then restore 3: the inspector first
  becomes Mass study and then silently reselects Support 3. The deleted ID
  remained in state. This was reproduced in the browser.
- The inspector says Selected object, but every available slider edits the
  entire composition. Selecting a support does not expose support-local edits.
- The camera resets on seed and height changes. There is no explicit Fit,
  Home or orthographic view control to separate navigation from generation.

Proposed fixes: select after a click-sized gesture, define a visible fallback
when a selected piece disappears, identify composition controls as global and
preserve the user's view during variation. Add explicit Fit/Home and front,
side, top and axonometric views. Show ratio units and their physical meaning;
for example, support height as both a percentage and millimetres.

### A06 — P2: Input and variation contracts need strengthening

The generator clamps finite ranges but does not reject non-finite values.
Passing `heightMm: NaN` produces non-finite geometry and volume; passing
`supportCount: NaN` produces an upper mass without supports. Range sliders do
not currently expose these values, so this becomes especially relevant before
project-file or numeric-input support.

All variation uses one sequential random stream. Existing unrelated controls
do not currently reroll choices, but adding a random draw earlier in the
generator would change later supports. Stable per-feature streams and lock
controls are still planned, not implemented. Semantic IDs should survive local
edits before operations, overrides and saved studies start depending on them.

Proposed fixes: one shared parameter schema for UI, loading and generation,
finite-value validation, a defined seed range and keyed random streams by
recipe/feature identity. Store the recipe version so later generator changes
do not silently reinterpret a saved project.

### A07 — P2: Viewport resource management will not scale with the model

Changing selection rebuilds every mesh, edge geometry and material because
the construction effect depends on both study and selected ID. The current
three-to-thirteen objects are small; repeated geometry allocation is still
unnecessary. The render loop also runs continuously while the scene is idle.

Unmount cleanup disposes the ground and grid but not the current model's
geometry/materials or the light's shadow resources explicitly. This is a
resource-lifecycle gap identified in code, not a measured long-session leak.

Proposed fixes: change materials for selection without rebuilding geometry,
dispose all owned resources on unmount, and consider rendering on demand while
continuing frames during damping and interaction. Add a visible fallback for
WebGL startup/context failures. Profile before adding workers or a new state
library; the current model does not justify either by itself.

### A08 — P2: Compact layout removes useful actions

At widths below 980 px the entire recipe/object panel is hidden. Below 680 px,
Next seed is hidden too, without an alternative. A 390 px browser confirmed
both omissions. The page does fit without horizontal overflow.

Proposed fix: collapsible drawers or tabs that preserve all actions. Expose
selected-object state to assistive technology, keep keyboard selection
available and provide numeric inputs alongside sliders. Mark unavailable
recipes as planned in clear product language rather than relying on DEFINED.

## Physical and product observations

### Weight should shape the early workflow

The default study is 1,080 × 510 × 1,500 mm and reports 0.587285 m³ of solid
material, approximately **1,409.485 kg** at the app's assumed 2,400 kg/m³.
At unchanged proportions, doubling every dimension multiplies this volume by
eight. A 1–2 m sculpture is therefore not automatically a manageable solid
cast. The current density is fixed and no centre-of-mass or support-polygon
calculation exists.

Prioritise editable density, separate concrete/core volumes and estimated
total mass, retained-core visualisation, and centre-of-mass/support-footprint
feedback alongside the solid kernel. Keep open voids, removable cores and
retained cores distinct. A core cannot be subtracted from the displayed mass
until it is also subtracted from the actual concrete solid.

The sweep also found shoulders with only about 45.3% of their top width under
the upper box. This is geometric contact information, not a load rating or
proof of failure. Show it as design feedback rather than automatically
removing an intentional overhang. Reinforcement, anchoring, handling and mould
loads remain outside the current software's verified capabilities.

### Complete one usable output path early

The viewport contains touching, separately closed pieces, not one boolean
union. Export is disabled, and no STL/3MF/SVG/G-code writer or Kerros/Muusia
adapter exists. Do not implement manufacturing export by concatenating the
preview meshes: shared internal faces must be resolved.

Validate the candidate solid kernel with touching faces, coplanar joins,
thin regions, explicit voids, volume agreement and memory cleanup. Then finish
one Piloti round trip: saved study, finished solid, scaled mesh and a verified
Kerros import. Keep face and core semantics available for the later package.

Prove a small real vector output early: front/side/top views and a simple
section, authored in millimetres. Define semantic path roles and page scale
before decorative drafting elements. Verify visible boundaries, absence of
duplicate strokes and triangle diagonals, and physical size in Muusia. Treat
axonometric hidden-line removal as its own technical spike; drawing all mesh
edges is not a finished blueprint. Machine-specific G-code remains Muusia's
responsibility.

### Suggested design direction

- Make the base a reusable support family: stem, neck, shoulder and bearing
  interface. Add row/grid layouts and shared/divided shoulders before
  decorative building details.
- Keep overall sculptural proportions separate from implied architectural
  scale. Board marks and service details should follow the latter.
- Develop monumental faceted Silos second, reusing the support vocabulary for
  tanks and hoppers and adding bridges/service cores as composition features.
- Introduce local feature locks and a small variant board after persistence;
  preserve a silhouette or selected base while varying other elements.
- Keep grey/white as the interface structure. Preserve semantic pink/blue
  cues with outlines or badges when yellow selection is applied.
- Add the RAAKA 1974 title block, revision mark and module notation after
  vector scale and path quality are verified. Plotter text needs a deliberate
  stroke-font or text-conversion policy, not accidental font outlines.

## Documentation and repository follow-through

This review adds explicit current-versus-planned status, removes the README's
suggestion that stability readings already exist, and links the audit from the
project entry points. The geometry fixes above remain open.

Consider explicitly writing `strict: true` for readability, but do not treat
its absence under TypeScript 6 as a defect. Source is public; the repository
has no LICENSE file. Record an owner-selected licence before inviting reuse
or contributions; this review does not select one. Hosting is still a future
decision: publishing source did not publish a hosted application.
